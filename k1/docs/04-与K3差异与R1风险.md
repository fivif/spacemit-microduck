# 04 · 与 K3 的差异对照 / R1 风险

> **结论先行**:K1 的 **ONNX Runtime 版本低于主仓地板** —— 这是立项时预判的 R1 风险,
> **实测确认会真的发生**(K3 没有这个问题,因为 K3 预装了 spacemit 定制 ORT)。

## 1. K3 vs K1 规格与实测对照

| 维度 | K3(实测) | K1(实测) | 影响 |
|---|---|---|---|
| 板卡 | K3 Pico-ITX | **MUSE-Pi-Pro** | K1 形态更适合真机 |
| CPU | 8× X100 @2.4 GHz | 8× **X60** @1.8 GHz | 单核 SPECint2006 **9.5 vs 3.5**(约 2.7×) |
| AI | 60 TOPS(8×A100 核 + spacemit EP) | **2 TOPS**(CPU `_ime` 融合) | 策略 MLP 不吃亏,都走 CPU |
| 内存 | 8 GiB(本机档) | **3.8 GiB**(4 GB 档) | 裁剪构建够用 |
| OS | Bianbu 4.0.1 | **Bianbu 2.3.3**(noble) | 同源,包版本不同 |
| glibc | 2.43 | **2.39** | 无影响(原生编译) |
| 内核 | 6.18.3-generic-riscv64 | **6.6.63** | 无影响 |
| **ONNX Runtime** | ✅ 预装 **1.24.2+spacemit.a1** | ❌ apt 只有 **1.18.1** | **R1 爆发点** |
| 实时核 RCPU | ✅ 600 MHz(直挂 CAN-FD/TSN) | ❌ 无 | P2 真机总线集成需评估 |

## 2. R1 风险:ORT 版本低于地板

### 事实链

| 环节 | 证据 |
|---|---|
| 主仓地板 | `Cargo.toml`: `[workspace.metadata.onnxruntime] floor = "1.23"`,注释明说"`ort` 在 1.23 以下会 panic" |
| `ort` 绑定 | `duck-control/Cargo.toml`: `ort = "=2.0.0-rc.11"`,features `load-dynamic`(dlopen,不编 C++) |
| K1 apt 包 | `onnxruntime 1.2.2`(**包版本号 ≠ ORT 版本号**) |
| K1 实际 .so | `libonnxruntime.so → .so.1 → libonnxruntime.so.1.18.1` |
| 结论 | **1.18.1 < 1.23 → 落在"会 panic"的区间** |

### 为什么 K3 没事

K3 的 Bianbu 4.0.1 **预装** `onnxruntime 1.24.2+spacemit.a1` + EP 主库,≥ 地板;
`ort` 用 `load-dynamic` dlopen 上去即可。K1 的 apt 源(`snapshots/v2.3`)里只有 1.18.1。

### 对策(按优先级)

| # | 方案 | 代价 | 备注 |
|---|---|---|---|
| **1** | **从 K3 搬 `libonnxruntime.so.1.24.2+spacemit.a1`** | **低** | ★ 首选。两板同为 riscv64、ABI 一致;依赖已核对(K3 的 ORT 要 `GLIBC_2.38`/`GLIBCXX_3.4.30`,K1 有 **2.39**/**3.4.32**)。脚本:[`../k1/fetch-ort-from-k3.sh`](../k1/fetch-ort-from-k3.sh)(本机)+ [`../k1/install-ort-k1.sh`](../k1/install-ort-k1.sh)(K1) |
| 2 | 在 K1 的 apt 源里找更新的包 | 低 | ⚠️ 包名不同:K1 装到的是 `onnxruntime`,K3 是 `spacemit-onnxruntime`;当时 `apt-cache search spacemit` 被 `head -20` 截断,未看全 —— 值得重查 |
| 3 | 自己编译 ONNX Runtime(riscv64) | 高 | riscv64 上编 C++ 很慢,但可控;产出标准 `libonnxruntime.so` |
| 4 | 用官方 riscv64 预编译包 | 中 | 需确认上游是否发布 riscv64 产物 |
| 5 | 降 `ort` 绑定版本 | 中 | 动到"代码零改动"前提,需验 API 兼容性 |

> **方案 1 的验证路径**:`probe-onnx.sh` 会 dlopen + 调 `OrtGetApiBase()->GetApi(23)`,
> 这正是 `ort` 初始化走的路径;通过即说明 R1 解除。

### 已核对的 ABI 兼容性(2026-09-08,K3 上 `readelf` 实测)

| K3 的 ORT 需求 | K1 实测 | 结论 |
|---|---|---|
| `GLIBC_2.38`(最高) | glibc **2.39** | ✅ |
| `GLIBCXX_3.4.30`(最高) | gcc 13.2 → **3.4.32** | ✅ |
| `ELF 64-bit UCB RISC-V, RVC, double-float` | 同架构/同 ABI | ✅ |
| NEEDED: `libatomic/libstdc++/libm/libgcc_s/libc` + `ld-linux-riscv64-lp64d.so.1` | 全部存在 | ✅ |
| 大小 | `libonnxruntime.so.1.24.2+spacemit.a1` **20 MB** + `libonnxruntime_providers_shared.so` 6 KB | 易搬运 |

> `robotd` 只用 **CPU EP**,**不需要** `libspacemit_ep.so`(那是 8×A100 AI 核专用,K1 本来也没有)。
> **唯一未知**:spacemit 的 ORT build 可能在初始化时 dlopen `libspacemit_ep.so`(非 NEEDED,运行时加载);
> K1 上无此库 —— 若硬性要求会报错而非优雅降级,只能上板实测(`probe-onnx.sh` 就是干这个的)。
