# 04 · 与 K3 的差异对照 / R1 风险

> **结论先行**:K1 的 **ONNX Runtime 版本低于主仓地板** —— 这是立项时预判的 R1 风险,
> **实测确认会真的发生**(K3 没有这个问题,因为 K3 预装了 spacemit 定制 ORT)。

## 1. K3 vs K1 规格与实测对照

| 维度 | K3(实测) | K1(实测) | 影响 |
|---|---|---|---|
| 板卡 | K3 Pico-ITX | **MUSE-Pi-Pro** | K1 形态更适合真机 |
| CPU | 8× X100 @2.4 GHz | 8× **X60** @1.8 GHz | 单核 SPECint2006 **9.5 vs 3.5**(约 2.7×) |
| AI | 60 TOPS(8×A100 核 + spacemit EP) | **2 TOPS**(CPU `_ime` 融合) | 策略 MLP 不吃亏,都走 CPU |
| 内存 | 8 GiB(本机档) | **3.8 GiB**(4 GB 档) | 裁剪构建够用 |
| OS | Bianbu 4.0.1 | **Bianbu 2.3.3**(noble) | 同源,包版本不同 |
| glibc | 2.43 | **2.39** | 无影响(原生编译) |
| 内核 | 6.18.3-generic-riscv64 | **6.6.63** | 无影响 |
| **ONNX Runtime** |  预装 **1.24.2+spacemit.a1** |  apt 只有 **1.18.1** | **R1 爆发点** |
| 实时核 RCPU |  600 MHz(直挂 CAN-FD/TSN) |  无 | P2 真机总线集成需评估 |

## 2. R1 风险:ORT 版本低于地板

### 事实链

| 环节 | 证据 |
|---|---|
| 主仓地板 | `Cargo.toml`: `[workspace.metadata.onnxruntime] floor = "1.23"`,注释明说"`ort` 在 1.23 以下会 panic" |
| `ort` 绑定 | `duck-control/Cargo.toml`: `ort = "=2.0.0-rc.11"`,features `load-dynamic`(dlopen,不编 C++) |
| K1 apt 包 | `onnxruntime 1.2.2`(**包版本号 ≠ ORT 版本号**) |
| K1 实际 .so | `libonnxruntime.so → .so.1 → libonnxruntime.so.1.18.1` |
| 结论 | **1.18.1 < 1.23 → 落在"会 panic"的区间** |

### 为什么 K3 没事

K3 的 Bianbu 4.0.1 **预装** `onnxruntime 1.24.2+spacemit.a1` + EP 主库,≥ 地板;
`ort` 用 `load-dynamic` dlopen 上去即可。K1 的 apt 源(`snapshots/v2.3`)里只有 1.18.1。

###  已解决(2026-09-09,K1 实测)

**解法就在板子上,不用跨机器搬。**

K1 已装的 `python3-spacemit-ort` 包内**自带一个更新的 ORT**:

```
/usr/lib/python3.12/dist-packages/onnxruntime/capi/
└── libonnxruntime.so.1.24.0+spacemit.a3     26.7 MB
```

| 检查项 | 结果 |
|---|---|
| 版本 | **1.24.0+spacemit.a3** ≥ 地板 1.23  |
| API v23(`probe-onnx.sh` dlopen + `GetApi(23)`) |  **可用** |
| `GLIBC_2.38` | K1 有 2.39  |
| `GLIBCXX_3.4.30` | K1 有 3.4.33  |
| `CXXABI_1.3.15` | K1 有 1.3.15  |
| `ELF 64-bit UCB RISC-V, RVC, double-float` | 同架构  |

**已安装到隔离目录**(不覆盖 `/usr/lib`,板上其它依赖 1.18.1 的程序不受影响):

```
/opt/microduck-k1/ort/
├── libonnxruntime.so -> libonnxruntime.so.1.24.0+spacemit.a3
├── libonnxruntime.so.1.24.0+spacemit.a3
└── libonnxruntime_providers_shared.so
```

用法:`export ORT_DYLIB_PATH=/opt/microduck-k1/ort/libonnxruntime.so`

> 注:该包在板上已安装,只是系统库路径指向的是 apt 的 1.18.1;显式指定 `ORT_DYLIB_PATH` 即可。

### 对策(按实际优先级,已被上表取代)

| # | 方案 | 代价 | 状态 |
|---|---|---|---|
| **1** | **用 K1 自带的 `python3-spacemit-ort` 里的 ORT** | **零** |  **已采用** —— 见上 |
| 2 | 从 K3 搬 `libonnxruntime.so.1.24.2+spacemit.a1` | 低 | 备选。两板同为 riscv64、ABI 一致。脚本 [`fetch-ort-from-k3.sh`](../k1/fetch-ort-from-k3.sh) + [`install-ort-k1.sh`](../k1/install-ort-k1.sh) |
| 3 | 在 K1 的 apt 源里找更新的包 | 低 | 已查:`snapshots/v2.3` / `noble-porting` / `plucky` 均只有 1.2.2(即 1.18.1) |
| 4 | 自己编译 ONNX Runtime(riscv64) | 高 | 兜底,未用 |
| 5 | 降 `ort` 绑定版本 | 中 | 动到"代码零改动"前提,未用 |

> **验证路径**:`probe-onnx.sh` 会 dlopen + 调 `OrtGetApiBase()->GetApi(23)`,
> 这正是 `ort` 初始化走的路径;通过即说明 R1 解除。
