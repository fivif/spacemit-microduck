# 05 · K1 联调实录:机器鸭换脑跑通(2026-09-09 / 09-10)

> **一句话**:K1 上原生编译的 `robotd`,经 SSH 反向隧道接本机 MuJoCo 数字孪生,
> 用官方 ONNX 策略完成**起身 → 站立 → 行走 → 转向**,全程未摔;
> 并部署了 Web 控制台,可用浏览器摇杆实时操控。

> 并把 `duck-detect` 接到本板 NPU provider 上(新增一个后端,不是重写)。
> **这是 K1 版的 P0 + P1 核心达成。**

### 40.7 Hz 这个数是谁的

上表里两条环率,条件都是**仿真跑在另一台机器、经 SSH 反向隧道**接过来。把这一跳单独量出来:

| 量 | p50 | p90 | p99 |
|---|---|---|---|
| 单次 `read`+`write` 往返(隧道) | 8.7 ms | 20.7 ms | 61.4 ms |

一个 tick 的预算是 **20 ms**。这一跳自己就吃掉 p50 的 43%,而 p99 已经是预算的三倍 ——
丢的帧是**隧道**丢的,不是板子算不过来。

把被控对象挪到板子本机再测同一个环:`stub-body.py` 说的是同一套 NDJSON 协议
(hello / read / write / gain / torque / slow),只把物理换成限速跟随器,策略仍然每 tick 真跑。
结果 **50.0 of 50.0 Hz、0 丢帧**,robotd 占 1.9% 单核,系统 98.5% 空闲。

**所以 40.7 Hz 应读作「隧道上限」,不是 K1 控制环的上限。**
它不推翻 K1/K3 的相对排序(两边的联调数都同样带隧道),但**不能**当成「K1 跑不动 50 Hz」的证据。
真机上没有这一跳,取而代之的是 1 Mbaud 舵机总线 —— 那是另一笔账,要等硬件到位才能量。

**结论**:K1 能跑通完整链路。表中「满载最低」一行**两边都是带隧道测的**,所以它是个**相对**读数 ——

(50.0 Hz / 0 丢帧 / 1.9% 单核),这一行**不能**读成「K1 算力不够跑 50 Hz」。
P2 真机集成真正要量的是舵机总线那一段。

## 视觉:K1 上的 `duck-detect`(2026-09-10 补测)

控制环之外,K1 上还补了一块:**把「找同类」的视觉检测器接到本板的 NPU provider 上**。
这块**不是移植,是加后端** —— 所以先说清楚边界。

### 为什么这里必须动代码

`duck-detect` 原来只有一条路:Rockchip 的 `librknnrt.so`(`src/rknn.rs`,靠 `dlopen`)。
K1 上那个运行时不存在,缺的不是算力,是**运行时本身**。新加的第三条路走厂商私有的 C 入口:

| | Rockchip(RK3566) | **K1(本次新增)** | 两者都没有 |
|---|---|---|---|
| 入口 | `librknnrt.so` 的 `rknn_*` | `OrtSessionOptionsSpaceMITEnvInit` | — |
| 模型 | INT8 `.rknn` | `.onnx`(opset 17) | 同左 |
| 运行时 | RKNN | ONNX Runtime 1.24.2 + spacemit EP | ONNX Runtime,CPU |
| 代码 | `src/rknn.rs`(未动) | `src/spacemit.rs`(**新增 256 行**) | `src/onnx.rs`(未动) |

要点是**没有第二条 ONNX 路径**:EP 挂到的是 `onnx.rs` 已经在建的那个 ort 会话,
输入张量、归一化、letterbox、decode 全是同一份代码。变的只是 ORT 把节点交给谁。

### 两个必须知道的实现细节

**1. `RTLD_GLOBAL` 不是可选项。** EP 里剩下的未定义符号是 `onnxruntime::…` 的 C++ 名字,
而它们**不在 `libspacemit_ep.so` 的 `DT_NEEDED` 里**(`readelf -d` 可查),靠进程全局作用域找。
`ort` 自己用的是 `libloading::Library::new`,也就是 `RTLD_LOCAL` —— 所以必须由我们先按**同一条路径**
把 `libonnxruntime.so` 以 `RTLD_NOW|RTLD_GLOBAL` 提起来,并在 EP 活着期间一直持有。
忘了这步的症状是 `undefined symbol: _ZN11onnxruntime…`,它不会告诉你是哪个 flag 的问题。

**2. EP 要先于 `/usr/lib`、在 Runtime 旁边找。** `spacemit-onnxruntime` 把 EP 放在
`ep/libspacemit_ep.so`,与配对的 `libonnxruntime.so` 并排;而 `/usr/lib/libspacemit_ep.so` 是
**另一个东西** —— 给 1.18 Runtime 用的 version 1 EP,两者不通用。搜索顺序从 `/usr/lib` 开始的话,
在同时有两者的板子上会找错那个,然后在别的地方以另一种方式失败。

### 模型必须换成 opset 13+

`duck_detector` 发布的 `duck_detect.onnx` 是 **opset 12**,`Split` 的尺寸还写在**属性**里。
EP 的形状推导没把它带下去,注意力块就按错误的形状编译:

```
operator compile failed at node (/model.10/m/m.0/attn/Reshape_2)[Reshape],
spine graph SpaceMITExecutionProvider_SpineSubgraph_…  error message:
The input tensor cannot be reshaped to the requested shape.
```

**这行报错不是真正的失败,真正的失败是它什么都不返回。** 打完这一行进程开始单核 100% 空转,
再也不出来 —— 实测 `timeout 45` 到点被杀(`exit=124`),45 s 内零输出、零帧。
一个把 daemon 挂死的检测器,读起来和形状问题毫无关系。

从 **opset 13** 起 `Split` 的尺寸改成**输入**,形状能传下去,同一份权重就编得过。
所以 `models/duck_detect.onnx` 现在存的是 opset-17 转换结果
(`onnx.version_converter.convert_version(model, 17)`),对这个图是**逐位相同**的:
12 帧 × 10 500 个输出,最大绝对差 **0.000e+00**。

### 实测(K1,`--hz 2`,测时板上无其他负载;1.6 GHz / `performance`)

```
runtime spacemit ep · onnxruntime 1.24.2+spacemit.a1
model 320×320×3, 10500 outputs
```

| | EP(SpaceMIT NPU) | CPU(ORT,2 线程) | 比值 |
|---|---|---|---|
| 延迟 p50 | **142.0 ms** | 718.5 ms | **5.1×** |
| p95 / p99 | 144.5 / 146.7 ms | 719.5 / 719.8 ms | |
| 每帧 CPU | **279.7 ms** | 1 439.7 ms | **5.1×** |
| 按 2 Hz 摊到单核 | **56%** | 288% | |
| 跑满(`--hz 0`) | 5.5 fps,单帧 p50 **200.0 ms** | — | |

**三件事要一起说:**

1. **EP 快 5 倍是真的** —— 单帧墙钟 142 ms vs 719 ms,每帧 CPU 280 ms vs 1 440 ms。
2. **但它不是「NPU 白干活」。** 2 Hz 下它仍占掉 **56% 的单核**。EP 只接管它认领的子图,
   其余节点回落到 CPU,前后的张量搬运也还在主机上。所以**不能**照抄 RK3566 那句
   「约占单核十分之一」—— 那块板的 NPU 路径是另一笔账。
3. **跑满反而更慢**(200.0 ms vs 142.0 ms)。2 Hz 的 500 ms 空档不是浪费:
   背靠背跑时 EP 的主机侧工作没有喘息,单帧就被拉长了。**这个数是「跑得动」,不是「该这么跑」。**

检测结果两边一致 —— 阈值 0.05 时 12 帧里 4 帧出框,**框坐标逐个相同**:

| 帧 | EP | CPU |
|---|---|---|
| frame_03 | 0.20 @ 451,759 | 0.20 @ 451,759 |
| frame_05 | 0.22 @ 391,795 | 0.22 @ 391,795 |
| frame_06 | 0.08 @ 320,793 | 0.08 @ 320,793 |
| frame_09 | **0.13** @ 138,709 | **0.14** @ 138,709 |

两遍独立测量结果相同。**这些是合成帧,只用来做等价性检查,不是精度评测** —— 默认阈值 0.35 下
一帧都不出框,那说明的是这批帧和这个阈值,不是模型。

### 一个必须保持的默认值

`session.disable_cpu_ep_fallback` **没有设,也不能设**。这个图有 EP 不认领的节点;
把这个开关打开,「EP 不管这个节点」就从一条慢路径变成**模型根本加载不了**。

### 判读

如果哪天在 K1 上看到 `duck-bench --backend spacemit` 输出 `runtime onnxruntime · cpu`,
说明 EP 没挂上(日志里那条 `warn` 会说为什么),此时检测仍在跑,只是慢 5 倍、吃 2.9 个核。
这一句横幅就是「到底谁在干活」的唯一凭据,`mediad` 的日志里同样有。

## 踩坑清单

1. **源码通过打包传输部署**(见 `docs/03`)。
2. **R1 的解法就在板子上** —— `python3-spacemit-ort` 自带 `libonnxruntime.so.1.24.0+spacemit.a3`,
   不必从别处搬。
3. **构建慢的真正原因是内存,不是 CPU** —— K1 只有 3.8 GiB 且**无 swap**,
   6 个 rustc 并行时(合计 ~1.9 GB)内存压力使内核反复回收页缓存,load average 飙到 **10.36**。
   若重来可用 `cargo build -j4` 换更稳的墙钟时间。
4. **`sit_toggle` 是切换,不是"起身"** —— 连按两次就坐回去了。日志里 `sit toggle direction="sit"/"stand"` 会显示方向。
5. **已折叠的鸭子不要用 `robot.init`** —— 它会用线性 ramp 重新归位,把折叠的鸭子拖倒
   (web 控制台 `server.py` 的注释写明了这一点)。正确姿势是 `sit_toggle`。
6. **本机只能跑一个 `body_server`** —— 多个实例抢 7801,只有第一个绑上,
   后启动的"重启"看着成功其实没生效(鸭子状态不变)。清理时注意每个实例还有一个 wrapper 进程。
   这个坑 2026-09-10 又踩了一次,而且症状会**伪装成隧道坏了**:连接建得上、发得出去,
   但 `recv` 立刻返回空 —— 因为应答来自那个僵住的旧实例,而它的 stdout 不是你在看的那个日志。
   排查顺序:先 `Get-NetTCPConnection -LocalPort 7801`,确认**只有一个** PID,再看隧道。
7. **浏览器和测试脚本会互相覆盖指令** —— `robot.move` 是 last-writer-wins,
   浏览器摇杆发的 `vx` 会和脚本发的值互相盖。调试时先关页面。
8. **`robotctl health` 默认读 `/run/robotd.sock`**,自建 socket 要传 `--robot-socket`
   (不是 `--socket`,后者是 updaterd 的)。
9. **仿真执行器是简化的** —— `duck-body` 用位置执行器,策略是在 BAM 摩擦模型下训的,
   速度跟踪只有 37–39%,**指令过猛容易摔**(实测 `vx=-0.40` 把鸭子开翻)。
10. **SpaceMIT EP 的未定义符号不在 `DT_NEEDED` 里** —— 必须自己用 `RTLD_NOW|RTLD_GLOBAL` 把
   `libonnxruntime.so` 提起来(`ort` 自己用的是 `RTLD_LOCAL`),否则只会看到
   `undefined symbol: _ZN11onnxruntime…`,而这句话不会指向 flag。
   另外 `/usr/lib/libspacemit_ep.so` 是给 1.18 Runtime 的 **version 1** EP,和 `ep/` 下那个不通用,
   搜索顺序必须从 Runtime 旁边开始。
11. **opset-12 的模型会让 EP 挂死,而不是报错** —— 日志里打一行
   `operator compile failed at node (/model.10/m/m.0/attn/Reshape_2)`,然后进程单核 100% 空转、
   再也不返回(`timeout 45` → `exit=124`,45 s 零输出)。换成 opset 13+ 就好。
   **看到那行 `operator compile failed` 不要等,直接 Ctrl-C。**
12. **在板上量延迟之前,先确认板上没有别的活** —— 同一套 `duck-bench` 参数,在板上还跑着一个
   `pip3 install onnx`(从源码编,一堆 `cc1plus`)时:EP 的 p50 从 **142.0 ms 抬到 182.0**、
   p99 从 **146.7 抬到 441.1**,CPU 后端 p50 从 **718.5 抬到 790.5**。
   数字还在,但已经不是这块板子的数字了。**先看 `ps` 和 `/proc/loadavg`,再信 benchmark。**

## 结论

**K1 版的 P0 + P1 核心达成**:riscv64 原生运行时 + 官方策略 + 数字孪生闭环 + 浏览器操控。
「用 SpacemiT K1 作为机器鸭大脑」在**软件层面成立**。
环率上也不再有余量疑问:摘掉联调用的隧道,板载环率是 50.0 of 50.0 Hz、0 丢帧、1.9% 单核。

**视觉侧同样是加法而不是重写** —— 新增一个 EP 后端(256 行),`duck-detect` 的其余部分、
`onnx.rs`、`mediad` 的取帧与解码全部未动;EP 加载时同一张图快 **5.1 倍**
(142.0 ms vs 718.5 ms),代价是 2 Hz 下 **56% 的单核**。这个代价要在真机上重新量:
它和 50 Hz 控制环抢的是同一批核。

剩下的只有真机硬件(舵机总线/供电/装机)—— 需硬件。
