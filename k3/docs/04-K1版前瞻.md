# 04 · K1 版对照

> 本文件写在 K1 移植之前,用作选型对照。**K1 实测结果见 [`../../k1/`](../../k1/)**。
> 下面第 4 条「平移策略」保留当时的预测原文,后面附了**事后对照**(2026-09-10)。
> K1 = SpacemiT 2024/12 芯片:8×X60 @1.8GHz、**2 TOPS 融合 AI(CPU 指令扩展内)**、16GB、10GB/s。
> 官方定位:AI 边缘计算机、AI+ 硬件、智能机器人、工业主控。

## 与 K3 的差异(对 Microduck 移植的影响)

| 维度 | K3 | K1 | 影响 |
|---|---|---|---|
| CPU | 8×X100 2.4GHz | 8×X60 1.8GHz | 单核差距明显(SPECint 9.5 vs ~3.5/GHz);50Hz 环 + MLP 仍富余(-40%) |
| AI | 60TOPS EP(onnxruntime+spacemit EP,1.24.2) | CPU 内 2TOPS;`spacemit-onnxruntime` 包同样提供 EP 库 | 策略 MLP 不吃亏,走 CPU;EP 只在视觉大图上有意义(见 04-K1 文档 §2) |
| 内存 | 32GB(本机 8G 档) | 16GB | 富余 |
| OS | Bianbu 4.0.1 | Bianbu(同源) | 无变化 |
| 板卡形态 | K3 Pico-ITX(2.5" SBC) | MUSE Pi Pro / MUSE Book / 实验箱 | **体积/功耗更好**:MUSE 形态是"换脑"的更好载体 → 真机集成的**推荐选项** |

## 平移策略(继承同一套方案)

1. **代码零改动**:K3 移植证明的是"RISC-V 通用可行性";K1 只是换 target/板卡。
2. 唯一验证点:BIANBU 上 K1 的 `libonnxruntime.so` 版本与 `ort rc.11` 兼容(同 R1 风险);
   策略默认走 CPU,无需改动(`policy.rs` 本来就是 CPU session)。
3. 媒体/NPU:同上裁掉;K1 的 2TOPS 融合指令(IME?)对检测器意义小。
4. 时序:K3 P0/P1 验收后,预计 1 天即可在 K1 复刻 P0(工具链已有)。

### 事后对照(2026-09-10)

| 预测 | 实际 | 差在哪 |
|---|---|---|
| 1. 代码零改动 |  **控制环确实一行未改**(`robotd` / `duck-control` / 策略) | 感知侧是加法:`duck-detect` 新增 `src/spacemit.rs`,把厂商 EP 挂到同一个 ort 会话上 |
| 3. 「媒体/NPU 裁掉,2TOPS 对检测器意义小」 |  **当时只裁了 `mediad`(GStreamer),`duck-detect` 没裁;`mediad` 的裁剪其后亦撤销** | K1 上检测器确实走 NPU(EP),而且值:同图 **142.0 ms vs CPU 718.5 ms = 5.1×**。原判断把"2 TOPS 的算力大小"当成了结论,真正卡住的是**有没有那个 provider 的接入口**。媒体侧同病相怜:`mediad` 编不过是板上缺 GStreamer 的 `-dev` 包,不是 riscv64 缺 GStreamer/厂商编码 —— 装齐后 K1 全量构建通过,USB 摄像头链路 MJPEG → UYVY → `spacemith264enc` 出实帧(2026-09-11) |
| 4. 预计 1 天复刻 P0 |  同日完成,结果见 K1 `docs/05` | 相符 |

细节(EP 的 `RTLD_GLOBAL` 要求、模型必须 opset 13+、2 Hz 下仍占 56% 单核)见
[`../../k1/docs/05-联调实录.md`](../../k1/docs/05-联调实录.md)。

## 决策预留(待 K3 真机集成反馈)

- 若 P2 发现 Pico-ITX 尺寸/功耗不合适 → **首选 K1 MUSE 形态**(更小、低功耗、12V?,已量产)——
  两条线可以同时呈现:一块偏性能,一块偏集成形态。
- K1 的 5 亿参数 20tok/s 特征对 Microduck 无关(机器人策略是 MLP,非 LLM)。
